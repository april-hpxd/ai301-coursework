# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff matches plan plus deviations | The candidate unified diff's changed files and behavioral edits, read against the plan-context In/Out scope (live: `plan.md` Scope plus `## Deviations`). See evidence-guide.md, Plan fidelity. | Every changed file and every behavioral change (new option, rewrite, extra feature) falls inside the plan's stated In-scope or a named deviation/deferral in the plan. Every In-scope deliverable the plan promised appears in the diff, unless the plan or an explicit deviation note defers it. Extra files, drive-by rewrites, or new config the plan scoped Out fail. An honestly deferred shortfall that the plan already named (and the description restates) is not drift. | required |
| Description matches the diff | The PR title and description's fidelity claims ("implements the plan exactly", "docs now updated", "no functional changes outside X"), read against the actual unified diff. See evidence-guide.md, Plan fidelity. | The description does not claim work the diff lacks, and does not claim exact plan fidelity or "no extra changes" when the diff exceeds the plan. Naming the issue and summarizing the in-diff change is enough. Claiming a docs/changelog/config change that is absent from the diff fails. | required |
| Test evidence is decisive | The test-evidence section (live: `test_evidence.md`) read against the plan's test plan and the original repro steps in the plan-context. See evidence-guide.md, Test evidence. | For each failure mode or repro step the plan named as in-scope verification, the evidence shows an observable before/after (or after plus a named before from the package) of that actual trigger — command and output, not "tests pass" or "verified on my machine". Evidence that only exercises a control/unchanged path fails. If the plan named several in-scope modes and the evidence is silent on one with no disclosed deferral, fail. A plan-noted deferral whose remaining in-scope repro is shown can pass. | required |
| Named verification commands were run | The plan's named suite/verification commands (e.g. `yarn test`, parser suite, the issue's pytest file) and any check outcomes the description claims, in the test-evidence section. See evidence-guide.md, Test evidence. | Every verification command the plan named has an observable outcome in the evidence (pass/fail transcript, or an honest "could not run X; ran Y instead" with Y shown). A description that claims a suite or check ran must show it. Do not fail solely because lint/CI/unrelated jobs are absent when the plan never named them and the description does not claim them. | required |
| Diff is reviewable | The unified diff and the commit list. See evidence-guide.md, Diff quality. | The fix is visible. The diff does not bury it under debug leftovers (stray print/eprintln/console.log that is not the fix), commented-out prior attempts, dead functions (`allow(dead_code)`, unused probes), pure re-indent/import-churn hunks unrelated to the change, or unrelated files. Explanatory comments on the fix are fine. | required |
| Template and policy honored | The repo-facts block's PR-template asks and stated contribution/AI policy (live: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`), read against the PR description and whether required files appear in the diff. See evidence-guide.md, Standards and comms. | Every stated required template ask has real content (issue close line if the template requires `Closes #`, filled checklist items that the package can actually satisfy, required sections not left as empty headings). If the template or contributing guide requires a changelog/whatsnew entry for the change, that file is in the diff. If the stated policy requires disclosing AI use, the description discloses it. Silence on AI passes only when the captured policy does not require disclosure. A required ask that is visibly ignored fails even when the code change is otherwise solid. | required |

## Verdict rule

Accept if every required check is graded `pass`. Any required check graded `fail` or `unclear` produces `reject`. Preferred checks never change the verdict. `unclear` means the evidence needed to apply the pass condition is genuinely absent from the package (for example there is no test-evidence section at all); treat `unclear` as fail for required checks. Do not reject a PR solely because it honestly discloses a plan-noted shortfall that remains out of the posted scope.
